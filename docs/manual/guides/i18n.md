# Localization

The engine is localized from the ground up: **no user-facing string is written
at a call site**. Every message the engine produces is a key plus parameters,
resolved against a catalog, and a lint enforces it.

This page is about that system, what a game can use of it today, and what it
cannot.

## The catalog format

Flat JSON, one file per locale, keys dotted and area-first:

```json
{
  "$comment": "English catalog.",
  "game.hud.score": "Score: {score}",
  "game.hud.lives": {
    "one": "{count} life left",
    "other": "{count} lives left"
  }
}
```

A value is **either a string or an object keyed by plural category**. The
category is chosen by a parameter named exactly `count`. English ships with two
categories — `one` for exactly 1 and `other` for everything else — and a locale
with more adds its own rule. A missing category falls back to `other`.

Placeholders are `{name}`. A trailing `.0` is trimmed from a number so counts
read naturally.

Adding a locale is **adding a sibling file**, with no code change. That is a
structural property rather than a promise: there is nowhere in the engine where
a string is concatenated at a call site, so there is nothing to go back and
change.

The fallback chain is the requested locale, then English, then the key itself
echoed with a one-time warning — a missing translation shows you *which* key is
missing rather than showing nothing.

## Three catalogs

They ship and are translated separately:

| Catalog | Covers |
|---|---|
| `i18n/en.json` | The engine. |
| `tools/cli/i18n/en.json` | The command-line tool. |
| `assets/i18n/en.json` | A game's own strings. |

## What a game gets today

**The game catalog is a convention with no reader.** There is no localization
service, and nothing loads `assets/i18n/en.json` into the game VM. The file is
scaffolded by the template and is carried through the asset pipeline, but a
script cannot ask the engine to resolve a key from it.

So a game that wants localized strings carries its own table:

```luau
--!strict
local Strings: { [string]: string } = {
    ["game.hud.score"] = "Score: {score}",
}

local function tr(key: string, params: { [string]: any }?): string
    local template = Strings[key]
    if template == nil then
        return key      -- echo the key, the same fallback the engine uses
    end
    if params == nil then
        return template
    end
    return (string.gsub(template, "{(%w+)}", function(name: string): string
        return tostring(params[name])
    end))
end

label.Text = tr("game.hud.score", { score = 42 })
```

Twelve lines, and it is honest about what it is. When a localization service
arrives, the call sites above are already the right shape.

## Why write keys now

Because the expensive part of localizing a game is not the lookup — it is going
back through every screen and finding the strings. A `tr("game.hud.score", …)`
written today costs nothing extra and is the whole of the migration later.

`InputBinding.DisplayName` already takes a key rather than a face-value string
for the same reason.

## Errors carry their key

Engine errors reaching Luau are pre-formatted with the key in front:

```text
[scene.err.parent_cycle] Cannot parent an instance to its own descendant.
```

That is what lets a test match on the key rather than on prose, and it is why a
conformance spec's `ToThrow` takes a plain substring.

## What the overlay does not do

The debug overlay's own labels are literals rather than catalog keys, and
deliberately: it exists for whoever is building the engine, never for a player.
The same reasoning applies to a GPU debug marker.
