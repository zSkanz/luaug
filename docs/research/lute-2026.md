# Lute Runtime — Research Report (as of 2026-08-19)

## 1. What Lute Is

**Official positioning: yes, first-party.** Lute lives in the `luau-lang` GitHub org alongside Luau itself, is MIT-licensed, and is staffed by the actual Luau team at Roblox.

- Repo: https://github.com/luau-lang/lute — description *"A standalone Luau runtime for general-purpose programming"*
- Docs site: https://lute.luau.org/ — tagline **"Run Luau Anywhere"**
- Created **2024-10-20**; default branch is `primary` (not `main`).
- Linked from the official Luau site footer ("Lute Runtime") at https://luau.org/

**Stated goal** (README): *"Our high-level goal with Lute is to build out the requisite tooling and support for Luau to work effectively as general-purpose programming language, not limited to its current use in Roblox."*

**Roblox-internal provenance** (README): *"In its current state, Lute provides a set of core runtime libraries that have already proven useful to us at Roblox in building both developer tooling for Luau and internal infrastructure projects."* The 1.0.0 release is explicitly framed as *"a stable version that this infrastructure could rely on."*

**Roblox convergence claim** (homepage, https://lute.luau.org/): the `@std` layer is intended to become a *shared* interface — *"For Roblox developers, we're working hard to ensure the Roblox game engine will support this same set of `@std` APIs in the future, so you can write code that runs both in Lute and Roblox with minimal changes."* Homepage bullet 3: *"Compatible with Roblox — Lute runs Luau code, just like Roblox, allowing you to easily run and test modules that don't depend on the game engine itself."* (This is language-level compatibility + `@std`, **not** a DataModel/Instance emulation.)

**Announcement history:**

## 3. Architecture & Implementation

**Languages: C++ core + Luau. There is NO Rust anywhere.** (Confirmed by reading `CMakeLists.txt` and `extern/` — no Corrosion, no cargo, no hyper/reqwest. That's Lune, not Lute.)

Three library sets (README):
1. **`lute/`** — core runtime in **C++**
2. **`std/`** — the `@std` standard library, written **in Luau**, embedded into the compiled executable
3. **`batteries/`** — standalone Luau libraries with no lute dependency, intended to be split out as independent packages later

**C++ module directories** under `lute/`: `batteries, cli, common, crypto, debug, definitions, fs, io, luau, net, process, require, runtime, std, syntax, system, task, time, vm` (19).

**Native dependencies** (from `CMakeLists.txt` + `extern/*.tune`):

| Dep | Role |
|---|---|
| **Luau** | language core (vendored + patched) |
| **libuv** | event loop / async I/O — *this is the backbone* |
| **curl** | HTTP client |
| **uWebSockets + uSockets** | HTTP/WebSocket server |
| **BoringSSL** | TLS/crypto |
| **libsodium** | password hashing, secretbox |
| **zlib** | compression |
| toml-test | test fixtures |

**Runtime structure — the embedding-relevant part.** Public headers at `lute/runtime/include/lute/`: `runtime.h`, `ref.h`, `userdatas.h`, `uvrequest.h`, `uvstream.h`, `uvutils.h`.

`runtime.h` defines a `Runtime` class wrapping a Luau VM + a libuv loop:
- Drive: `runToCompletion()`, `runOnce()` → `RuntimeStep`, `runContinuously()` (blocking; *"for child runtimes"*)
- Schedule: `schedule(std::function<void()>)`, `scheduleLuauResume()`, `scheduleLuauError()`, `scheduleLuauCallback()`, `scheduleDebugLuauCallback()`
- Execute: `runSource()`, `runBytecode()`
- Loop access: **`getEventLoop() -> uv_loop_t*`**, `runInWorkQueue()`
- Lifetime: `addPendingToken()` / `releasePendingToken()`, `addThreadCompletionHandler()`, `reportError()`
- **`ResumeToken`** struct — the documented async extension point for native code: `fail(std::string error)` and `complete(std::function<int(lua_State*)> cont)`
- **`setupState()`** takes a callback for sandbox configuration before execution begins

**Single vs multi-VM: multi-VM, with a very thin scripting-side surface.** `@lute/vm` currently exposes **exactly one function**: `vm.create(path: string)` → *"Creates a new Luau VM from the module at path and returns its exported table."* Each call produces an isolated VM. The `runContinuously()` comment ("for child runtimes") implies child runtimes run their own loop, presumably on separate OS threads. The C++ side clearly supports N `Runtime` instances; the Luau-facing API is deliberately minimal at this stage.

**Task scheduler: coroutine-based, resumption-cycle model over libuv. Not async/await, no promises.** `@lute/task`:
- `task.spawn(routine)` — run on the next resumption cycle
- `task.defer(routine)` — run after the current thread yields
- `task.delay(dur, routine)` — `dur` is seconds or a `time.Duration`
- `task.wait(dur?)` — yield for `dur` seconds, or until next cycle
- `task.resume(thread)` — run until yield/completion
- `task.deferSelf()` — yield and reschedule self next cycle

This is deliberately Roblox-shaped (`task.spawn`/`defer`/`delay`/`wait` mirror Roblox's `task` library) — a major ergonomic win for the "developers coming from Roblox" audience.

**I/O sync vs async:** `@lute/fs` signatures are **synchronous-looking** from Luau (`fs.read`, `fs.write`, `fs.open`…) but are implemented on libuv, so they yield the calling coroutine rather than blocking the loop. Streaming APIs do **not** exist yet — that's issue #128 (below).

## 5. Extensibility & Embedding

This is the weakest-documented area and the biggest risk for a "Lute as engine host" option.

**Can Lute be embedded as a library into a larger native app?** *Technically yes, officially no.*

Evidence **for**:
- Clean modular CMake target layout: separate library targets for `batteries, common, definitions, require, runtime, crypto, fs, luau, net, std, task, vm, process, system, time, io, syntax, debug`; only `cli` and `tests` are executables. You can `add_subdirectory()` Lute and link the pieces you want.
- `lute/runtime/include/lute/runtime.h` is a genuine public header with a usable `Runtime` API (`runSource`, `runBytecode`, `getEventLoop()`, `schedule*`, `setupState()` sandbox hook).
- **`LUTE_EXTERN_C`** CMake option (CMakeLists.txt ~line 113): *"Use extern C Lute API functions"* — when ON it sets `LUAU_EXTERN_C ON`, forcing Luau to use `longjmp` instead of C++ exceptions. This exists precisely so Lute's public surface can be consumed across a C ABI boundary.
- `-DLUTE_STDLESS=ON` builds the runtime without the embedded `@std`, i.e. a bare runtime core.

Evidence **against**:
- **No `install()` rules in the root `CMakeLists.txt`** → no exported CMake package, no `find_package(Lute)`, no versioned/installed headers. You'd vendor the source tree as a submodule.
- **No embedding documentation whatsoever** on lute.luau.org (no "Embedding" section; guide is Installation / Hello World / Guessing Game / Writing Tests / Code Transformations / Developer Tooling / Docker).
- No C++ standard set in the root CMakeLists (delegated to subdirs), min CMake 3.13.
- No public examples of anyone embedding Lute found.

**Can third parties add native modules?**
- **Today: only by forking / building from source and adding a CMake subdirectory + registering the library in the runtime's state setup.** There is no dynamic-loading mechanism (no `.so`/`.dll` module loader, no `require` of native libs).
- Issue **#1047 "Support for loadable native modules"** (https://github.com/luau-lang/lute/issues/1047) — opened by **OMouta on 2026-04-23**, labels `enhancement` + `runtime`, **still open, unassigned, no milestone, no visible maintainer response after ~4 months**. The request explicitly cites *"graphics bindings, system APIs, performance-critical modules, and compiled library integrations."* This is *exactly* the game-engine use case and it is currently unanswered.
- Issue **#1064** (closed 2026-07-29 by tapple) added `--defs` to `lute check` specifically to work *"with custom luau embeddings"* — a small but real acknowledgement that people embed Luau alongside Lute tooling.

**The realistic extension path today** for a custom native module: fork or submodule Lute, add your C++ library target, register your library table in `setupState()`, and use `ResumeToken::complete(std::function<int(lua_State*)>)` to resume Luau threads from your async native work. That is a supported-by-construction pattern (it's how `fs`/`net` themselves work) but it is undocumented and unversioned — you'd be tracking `primary` or a release branch by hand.

## 6. Build & Platforms

**Build system:** CMake (min **3.13**) + **Ninja**, orchestrated by **`luthier`** — a build tool the Lute team wrote **in Luau, run by Lute itself** (dogfooding). Located at `./tools/luthier.luau`. `luthier generate` performs the codegen that embeds the CLI frontend commands and `@std` into the executable.

Three build paths (README):
1. `./tools/bootstrap.sh` — builds `lute0` (minimal debug build, `-DLUTE_STDLESS=ON`, no embedded std), then uses `lute0` to run codegen and produce the full release executable. `--install` puts it at `$HOME/.lute/bin/lute`.
2. Toolchain managers: **`foreman`** (`foreman.toml`) or **`rokit`** (`rokit.toml`) to install prerequisites.
3. Manual cmake/ninja with hand-fetched externals.

CMake options: `LUTE_ENABLE_SANITIZERS`, `LUTE_STDLESS`, `LUTE_OPTIMIZE_SIZE`, `LUTE_EXTERN_C`. ccache supported via `--with-ccache` (needs `CCACHE_DIR`, `CCACHE_MAXSIZE`, `CCACHE_COMPRESS`).

## 7. Runtime Features Relevant for Tooling

**CLI surface** (https://lute.luau.org/cli/): `run`, `test`, `lint`, `check`, `compile`, `transform`, `pkg`, `setup`, `self`. Syntax `lute <command> [options] [args...]`, with `-h/--help` and `--version`.

| Command | Detail |
|---|---|
| **`run`** | Default — `lute script.luau` == `lute run script.luau`. **Built-in sampling profiler**: `--profile` (default **10,000 Hz**), `--profile-output <file>`, `--frequency <Hz>`; emits JSON traces for **ui.perfetto.dev**. Currently **single-threaded code only**. |
| **`compile`** | **`lute compile <entry.luau>` → standalone executable.** Bundles entry + all dependencies. `--output <path>` (defaults to entry basename, `.exe` on Windows), `--bundle-stats` (bytecode size + compression metrics), `--show-require-graph` (dependency tree). |
| **`check`** | Runs the Luau type checker. `--defs` for custom embeddings (#1064). |
| **`lint`** | Config in **`lint.config.luau`** (Luau-as-config, deliberately avoiding TOML/JSON mixing). `--output` flag for diagnostics format added in a 2026 nightly. Custom per-project lint rules supported. Open PR #1158 adds config overrides. |
| **`test`** | Discovers `*.test.luau` and `*.spec.luau`, defaults to `tests/`. `--list`, `-s/--suite`, `-c/--case`. Assertions/runners live in `@std/test`. No documented coverage, parallelism, or snapshot support. |
| **`transform`** | CST-based codemods; there's a dedicated walkthrough in the guide. Open PR #1136 wants a dynamic build system for it. |
| **`pkg`** | `lute pkg install`. Deps declared in **`loom.config.luau`** ("loom" is the package-manager identity). Packages fetched **from GitHub**. Auth chain: `GITHUB_TOKEN` env → custom credential providers configured in `.config.luau` (can shell out to `gh` CLI) → plaintext store at `~/.loom/auth.luau`. **Lockfile-based dependency resolution** landed in a 2026 nightly. |
| **`setup`** | Generates type definition files for the language server. **`--with-luaurc`** writes the aliases into your project's `.luaurc` automatically. |
| **`self`** | Manages the Lute install under `~/.lute`. |

**REPL: none documented.** No `lute repl` in the CLI reference. (Upstream `luau` the binary has a sandboxed REPL; Lute does not appear to expose one.)

**Require resolution / `.luaurc`:** Lute has a dedicated C++ `lute/require` module and uses standard Luau require-by-string semantics — `.luaurc` aliases, `@self` (reserved, resolves relative to the calling file's directory), `init.luau` for directories. `lute setup --with-luaurc` writes `@lute`/`@std` aliases in. Script-side: `@lute/luau.resolveModule(path, fromchunkname)`, and open PR **#908** adds `luau.resolveConfig`. Recent nightlies fixed "module resolution for ambiguous directory requires". Issue **#1015** (opened 2026-04-19) proposes a unified **`project.config.luau`** to replace the scatter of `wally.toml` / `rokit.toml` / `*.project.json` / `lint.config.luau`.

**Debugging:** Real and rapidly maturing. `@lute/debugger` (§4) plus 2026 nightlies that shipped stepping, thread inspection, variable inspection, stack traces, global-variable tracking, and thread-ordering fixes. Open PRs **#1291 exception breakpoints** and **#1290 evaluate expressions**. **No explicit DAP (Debug Adapter Protocol) implementation** — the API is callback-driven (`onBreakpointHit`, `onStepStop`, `LaunchConfig`), which is DAP-*shaped* but you'd write the adapter.

### How the community sees it

- **Lute team's own framing** (HN 2026-04-22, comment from a Lute team member): the two are *"pretty similar right now"*, but Lute has *"more of a focus on being general purpose"* whereas Lune has *"e.g. Roblox file format parsing as a core feature"*; the decisive Lute advantage is exposing **Luau's parser**, *"which we're using to build more developer tooling for Luau, including a linter, a codemod tool, and a package manager."*
- **Lune is not deprecated** and no maintainer has announced a wind-down. There are **zero issues in the Lune repo mentioning "Lute."**
- **But the migration signals are strong:**
  1. **Nicell (Nick Winans)** — previously publishing Lune Docker images (`hub.docker.com/r/nicell/lune`) — is now the **#5 contributor to Lute (81 commits)** and is the maintainer triaging Lute's std API design (he authored issue #128 on Streams). He's a Roblox engineer.
  2. **JohnnyMorganz** — author of **luau-lsp** and **StyLua**, the two most-used Luau tooling projects — is the **#8 Lute contributor (43 commits)**. Tooling gravity is moving to Lute.
  3. Nicell's **Lynx** web framework (https://github.com/Nicell/lynx) is explicitly *"A Simple and Fast Luau Web Framework for **Lute and Lune**"* — i.e. the ecosystem is currently writing **dual-target** libraries, which is the classic transition phase.
  4. Activity delta: 562 vs 62 commits/year; Lune had a ~8.5-month release gap and 7 consecutive weeks of zero commits.
  5. `@std` is being positioned as the **shared cross-runtime interface** with Roblox engine support promised — Lune has no equivalent standardization story.

**Verdict for the LuauG plan:** Lute is becoming the standard for standalone Luau, especially for anything *tooling*-shaped. Lune remains the better choice only if you need `.rbxl`/`.rbxm` parsing or a Rust embedding story today.

## 11. Assessment For The LuauG Plan (derived, not sourced)

**(a) Lute as the runtime for engine tooling/CLI — STRONG FIT, recommend.**
- You get for free: `.luaurc`-aware require resolution, type checking, linting, a test runner, a CST parser for codegen/codemods, a package manager, a file watcher (dev server), an HTTP+WebSocket server (dev server / hot reload channel), a process runner (shelling out to shader compilers, texture converters), crypto digests (content-addressed asset hashing), nanosecond timing, a sampling profiler, and `lute compile` to ship your CLI as a single binary.
- Your tooling scripts would be written in **the same language your users write gameplay in**, with a **Roblox-shaped `task` API** — enormous onboarding win for the Roblox-migrant audience.
- Main gaps to plan around: **no streaming I/O** (#128) — large asset streaming and subprocess pipe handling need workarounds; **thin `io`** (no flush, no tty yet); **no macOS Intel binary**; **API churn risk** despite 1.0 (every module carries the breaking-change banner).

**(b) Lute as the host runtime the engine extends with native modules — WEAK FIT today, high risk.**
- There is **no dynamic native module loading**, **no documented embedding API**, **no CMake install/export**, and the one issue asking for exactly this (#1047) has sat unanswered since April 2026.
- You would be **forking or submoduling Lute and building it as part of your engine**, registering your renderer/input/audio libraries via `setupState()` and driving `Runtime::runOnce()` from your frame loop, resuming Luau from native async work via `ResumeToken`. That is architecturally coherent (`getEventLoop() → uv_loop_t*` is genuinely useful) but you'd own the merge burden against a repo doing ~11 commits/week with unfrozen internals.
- **Consider the alternative:** embed **plain Luau** (which has a mature, documented C API and an explicit "embeddable language" positioning per the 2025 runtime recap) for the *game* runtime, and use **Lute unmodified, as a binary**, for the *tooling* runtime. That gets you `@std` compatibility across both without inheriting Lute's build system. The convergence bet — `@std` becoming the shared interface across Roblox / Lute / other engines — makes implementing `@std` in your own engine runtime the strategically-aligned move.

## Addendum — 2026-08-20 (M4)

The body is a frozen snapshot and is not edited; corrections live here.

**§7's CLI surface is wrong against the pinned artifact.** The body lists
`run`, `test`, `lint`, `check`, `compile`, `transform`, `pkg`, `setup`, `self`,
sourced from `lute.luau.org/cli/`. The installed Lute 1.0.0 answers `--help`
with six commands:

```
run (default)   Run a Luau script.
check           Type check Luau files.
compile         Compile a Luau script into a standalone executable.
setup           Generate type definition files for the language server.
transform       Run a specified code transformation on specified Luau files.
lint            Run linting rules on specified Luau files.
```

So **`pkg` and `self` do not exist** at 1.0.0. And `test` — which this
repository's own gate depends on, since `scripts/gates/luau-check.sh` runs
`lute test tools/cli/tests` — **works but is not listed in `--help` at all**.
An undocumented-but-present command is the more useful half of this correction:
a future session reading `--help` to decide what Lute can do would conclude the
gate's own test runner does not exist.

Found while implementing `luaug --version`, which needed a version number from
the interpreter. Two further observations from the same probe, both confirmed
by running rather than by reading:

- **Nothing in-process reports Lute's version.** `_VERSION` is the string
  `"Luau"`, and no module in the installed 1.0.0 typedefs mentions a version.
  `lute --version` prints `1.0.0` and a newline; asking
  `process.execPath()` rather than `lute` on PATH is what makes the answer be
  about the interpreter actually running.
- **`ProcessResult`'s exit field is `exitcode`, not `code`.** `result.code`
  reads `nil` — silently, which is the shape of a check that always passes.
